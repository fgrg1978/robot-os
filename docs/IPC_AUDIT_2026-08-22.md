# IPC Subsystem Audit — 2026-08-22

Sweep of `crates/ipc/` (5,709 lines, 21 modules) plus its arms in
`crates/syscall/src/dispatch.rs`. The focus is dual by explicit request:
IPC is the path this kernel **optimizes**, so each finding is judged by
security *and* by latency.

## Measured baseline (not inferred)

`userspace/latbench` on QEMU virt, `-smp 4`, build `--release --features qemu`,
machine at rest, 2000 ops per batch:

|---|---:|---:|

## The class: bare id without caller authorization check

Known signature pattern (`feedback-fix-the-class-not-the-instance`): a public
function that takes a resource id and **does not receive the caller's tid**,
so it cannot authorize even if it wanted to. Complete sweep:

| function | authorizes? | reachable from ring 3? |
|---|---|---|
| `handle_revoke/dup/check` | yes (W2-C3) | yes |
| `port_*` | via `port_access_ok` in dispatch (W3-F2) | yes |
| `io_ring_*` | via `io_ring_access_ok` in dispatch (W3-F3) | yes |
| `shm_*` | yes, by owner (W3-F1) | yes |
| **`fast_ipc_reply(slot_idx, words)`** | **NO** | **yes — `SYS_IPC_FAST_REPLY`** |
| **`lease_return(lease_id)`** | **NO** | **yes — `SYS_IPC_LEASE_RETURN`** |
| **`lease_free(lease_id)`** | **NO** | **yes — `SYS_IPC_LEASE_FREE`** |
| `channel_send/recv/destroy(ch)` | NO | yes — `SYS_CHAN_*` |
| `pipe_read/write/close_*(idx)` | NO | yes |
| `pipeline_*` (zerocopy) | NO | **no** — no syscall arm |
| `signal_send(tid, sig)` | NO | yes |

`zerocopy` is outside the scope of security: it has no syscall surface,
it is internal to the kernel.

## Findings in `fast_ipc.rs` (batch 1)

### IPC-1 · `SYS_IPC_FAST_REPLY` does not authorize — server impersonation
`fast_ipc_reply(slot_idx, words)` does not check that the caller is the
`server_tid` of the slot. `server_tid` is written in `alloc_slot` and only
read in `find_pending_for_server`: a field written and never read for authorization,
the same signature as `HANDLES`, `port`, `io_ring`, and `shm`. Fifth instance.

The index ranges from 0 to 63 and the dispatch arm takes it raw from `a0`. A
ring-3 task iterates all 64 and, for each live slot, writes arbitrary words
and wakes the client. The client returns from its call with the attacker's data
believing it came from its server.

### IPC-2 · Slot enters `Replied` before reply exists
`fast_ipc_accept` marks `SlotState::Replied` with the comment
"temporarily reuse state to mark accepted", while the slot's words are still
**the request**. `find_reply_for_caller` matches exactly by `Replied`. A server
that accepts and dies leaves the client picking up its own request as a reply.
No attacker needed.

### IPC-3 · Slot leak: no reclamation in `task_exit`
`task_release_all` (`crates/ipc/src/lib.rs`) calls exactly three things:
`handle_revoke_all`, `cap_store::reset`, `shm_release_all`. Nothing for
`fast_ipc`, `port`, `io_ring`, `lease`, `rpc`, or `pipe`. `rpc_cancel_all(tid)`
exists and **has no callers anywhere in the tree**.

Specific consequence for the fast path: when all 64 slots are exhausted,
`fast_ipc_call` returns `None` forever and the dispatch arm responds with
`-1`, whose documented contract is "fall back to IPC via channel". **The fast
path goes dead and no test fails.** It is a latency regression masquerading as
a leak, and that is why it belongs in this pass and not another list.

### IPC-4 · Lost wakeup — fast path hangs on SMP
`try_wake_task` exits early if `state != Blocked`. The sequence of
`SYS_IPC_FAST_CALL` is: allocate slot → `wake_fast_ipc_server` → `task_block`.
With multiple harts the server can accept and reply **before** the client
reaches the block point; the wakeup is lost and the client sleeps forever,
holding the slot (feeds IPC-3). Symmetric in `FAST_ACCEPT`.

The kernel **already has** the remedy: K-C9 added `Task::wake_pending`, which
`block_current` consumes just before committing to `Blocked`. But only
`wq_wake_by_tid` *writes* it; `try_wake_task` —the path for all
`wake_*` in `wait.rs`— never sets it. Sixth instance of the class.

### IPC-5 · `fast_ipc_call` does not validate `server_tid`
A call to a nonexistent TID allocates a slot, wakes no one, and blocks the
caller forever. Self-inflicted, but it is a free slot leak from ring 3.

### Coverage
`SYS_IPC_FAST_CALL/ACCEPT/REPLY` **have no wrapper in `crates/libsys`**.
No ring-3 program has ever executed the fast path. That is why all five
findings survived every prior pass.

## Measurement note: a false positive I almost reported as regression

After landing the four lanes, the clean `-smp 4` scenario showed **36**
`[ISR-WCET]` events (sum of `lease_tick` = 143 ms, max 26 ms) versus
**3** on HEAD (sum 5.3 ms, max 2.7 ms). Twelve times more events in the
timer ISR, right after a lane touched `lease_tick`. Fit too perfectly.

It was not a regression. Two things betrayed it:

1. Labels that **no one touched** — `vdso_update` and `wake_expired_timers` —
   also crossed the 1 ms threshold for the first time. A change in `lease.rs`
   cannot slow down the vDSO updater.
2. Rerunning with **the same binary** at a quieter time gave **1** event
   and 1.0 ms. Same code, same command, two orders of magnitude difference.

The culprit was the ring-3 probe lane itself, launching QEMU in parallel.
It is exactly the trap that bit us this week with the userspace scenario,
and why `ci_check.sh` carries no clock thresholds: a time ceiling measures
host load, not the kernel.

Paired comparison, with noise controlled: HEAD and the new tree each give
**1 event**. At TCG noise level with another QEMU alive, the instrument
—a 1 ms threshold— is too coarse to resolve anything here.

**What this does NOT prove:** that `lease_tick` did not get more expensive.
It now also expires `Pending` leases, so it does strictly more work per
tick, and runs inside the ISR. Remains to measure it with the machine quiet
and a finer instrument than a millisecond threshold.

## Findings from ring-3 probe (outside IPC scope)

The `userspace/ipctest` probe is the first ring-3 program in the tree that
calls `fork()` and uses it for something. It found two kernel defects unrelated
to IPC.

### K-C11 · `fork()` does not deliver parent's register file to child
**CONFIRMED by reading code, not just by symptom.**

`fork_child_entry` (`crates/sched/src/process.rs:767`) receives a fork context
of exactly three fields — `(entry, user_sp, satp)` — and enters user mode via
`sret_to_user` (`:412`), which writes `sepc`, `sstatus`, `sscratch`, `satp`,
and `sp`, and zeros `a0`–`a7`. **No one copies `ra`, `gp`, `tp`,
`t0`–`t6`, or `s0`–`s11`.** The child resumes user code with whatever those
registers held in the *kernel task* that launched it.

For initial `exec` of a fresh ELF that is correct: at the entry point
registers are not defined by the ABI, and zeroing them is desirable.
For `fork()` it is simply wrong — the child must continue the same
function as the parent, and the compiler keeps values live in `s` registers
across the `ecall`.

Two consequences, both measured by the probe, not supposed:
- **Correctness.** A canary in `s11` survives in the parent but not the child.
  With the child's index passed by register, all eight children thought they
  were number 0. Worse: the compiler materialized a `static` address into
  `s10` before the `ecall` and emitted `sd s11,24(s10)` after; in the child
  `s10` held a kernel address and the result was `[PAGE FAULT] Killing user
  task`. Any child is one hoisted base register away from death.
- **Security.** It is a kernel-to-ring-3 state leak: in the trace we see
  `regs[1] (ra) = 0x8020198a`, a kernel code pointer delivered to a user
  task. It defeats any ASLR and serves as a layout oracle.

Fix: the fork context must carry the parent's complete register file at
the moment of the `ecall`, and the child's entry must restore it. It is
not a one-liner and touches `crates/sched`.

### K-C12 · `fork()` returns positive TID for children that never execute
Observed rate ~30%: of eight children five appeared, no failure, no trace,
no `[FORK] still waiting` diagnostic. Not isolated. Could be K-C11 biting
another path, or pool slot reuse. **Not confirmed by code reading** —
only by symptom reproduced in three runs.

### K-C13 (minor) · Truncated read executes as if complete
Under host contention, `[VIRTIO-BLK] request timeout - device reset, block
I/O disabled` was followed by `[AUTORUN] Read 29264 bytes, exec'ing...` and
`Illegal instruction` at entry. Autorun does not check whether the device
disabled mid-read.

## K-C11 closed and verified

`fork()` now delivers the parent's complete register file to the child.
Change: `Task::fork_regs: [u64; 32]` (256 B per slot, 16 KiB with
`MAX_TASKS`=64, in BSS), populated from the trap frame and consumed by
`sret_to_user_forked`, which restores `x1..x31` and forces `a0 = 0`.

Verified with the ring-3 probe's canary, not by reading:

```
before:  child_main role=2 tid=26 s11=17168          (kernel garbage)
after:   child_main role=2 tid=26 s11=1526644958     (= 0x5AFEC0DE, parent's)
```

Three decisions worth not undoing:

- **`tp` is NOT restored.** In this kernel `tp` carries the hart id:
  `current_cpu_id()` reads it, and `trap_entry.S` saves the `tp` the user
  brought **and never restores a kernel one**. A child inheriting the
  parent's `tp` and dispatched to another hart would make the kernel address
  another CPU's `PER_CPU` on its first syscall — the K-A11 corruption,
  reintroduced by the fix. We preserve the kernel `tp` with which the child's
  entry already runs, which is correct for its hart and identical to prior
  behavior. No TLS in this tree.
- **That `trap_entry.S` puts user-controlled `tp` in kernel context is a
  separate finding**, neither created nor closed here: ring 3 can write `tp`
  and make the kernel address the wrong hart.
- **The register file is copied by value onto the stack** before `csrw satp`.
  Reading `TASKS[idx].fork_regs` after page-table switch would silently
  depend on `copy_kernel_entries_to_user` mapping the kernel's `.bss`;
  getting it wrong is an S-mode fault under `panic = "abort"`,
  that is board reset **on every fork**. Kernel stack is reachable after
  switch — the preexisting `csrw sscratch, sp` already assumes it.

`sret_to_user` (fresh exec) is left untouched: zeroing registers at ELF entry
is correct by ABI and is what prevents that path from leaking kernel state.

## Instrumentation: `ipc-trace` feature

`cargo build --features qemu,ipc-trace` traces every CALL/ACCEPT/REPLY on the
fast path, including the block and wakeup of each retry loop turn.
**Off by default and should stay that way**: each line is a UART write, which
costs ~160 µs per 64 bytes on QEMU. It does not observe the fast path, it
replaces it. Good for "where the exchange stalls", never for "how long it takes".

## Phase A: precise diagnosis, root cause still open

With tracing, the exchange **completes** and the failure narrows to one point:

```
[IPC] CALL  tid=120 -> srv=17 w0=0x110000
[IPC] CALL  tid=120 slot=1 claimed
[IPC] CALL  tid=120 slot=1 blocking (turn 0)
[IPC] ACCEPT srv=17 slot=1 (no block)
[IPC] REPLY  srv=17 slot=1 w0=0x220001
[IPC] REPLY  srv=17 slot=1 woke client tid=120
                                        ← `woke (turn 0)` NEVER appears
```

The first four exchanges allocate slot, accept, and reply correctly. The client
blocks, the reply is deposited, the wakeup is sent — `wake_task_by_tid` sets
`Ready` and enqueues — and **the client is never scheduled again**. No
`SYS_IPC_FAST_CALL` returns in the entire run.

Ruled out:
- Not K-C11 (fixed and verified; phase A unchanged).
- Not lost wakeup: the wakeup is sent *after* the client prints it will block,
  and with `wake_pending` flag if it arrived before.
- Not authorization: `REPLY` succeeds and returns the correct TID.
- Not the entire scheduler: the server keeps running and exhausts its eight
  `ACCEPT` turns afterward.
- Not page faults: they are COW and resolve.

Remains to rule out: which CPU the client ends up enqueued on
(`cpu_enqueue_locked` falls back to CPU 0 when `cpu_affinity < 0`), and whether
the spin gate on `context_saving` intervenes. That is the next step.

## K-C14 · All wakeups without affinity went to CPU 0 — CLOSED

The three wakeup paths (`try_wake_task`, `wq_wake_by_tid`,
`wake_task_by_tid`) sent every unfixed task to **CPU 0**, unconditionally.
`find_least_loaded_cpu()` lived in that same file forever and none called it.

Not a load imbalance: it is reproducible starvation. `cpu_dequeue`
picks by `ready_bitmap.trailing_zeros()`, that is strictly by priority, and
at default startup CPU 0 is where real-time tasks live
(`rt-motor` and `flight-ctrl` are created with hart 0 affinity). So **every
unfixed task that blocks and is woken** —any that does IPC, I/O,
or sleeps— is rebound forever behind two RT tasks on a single hart,
however idle the other three are.

Measured, not reasoned: phase A completed exactly as many exchanges as
clients remained on their post-fork CPU — four — then stalled. With the fix,
`SYS_IPC_FAST_CALL` goes from **0 returns to 7** in the same window.

What made this bug so expensive to find: the kernel is still healthy, RT tasks
meet their deadlines, no error in any log, and clients are `Ready` and correctly
enqueued. **It reads exactly like a lost wakeup and is not.** I chased lost
wakeup for hours.

## K-C15 · Wakeup between CPUs does not send IPI — OPEN

With K-C14 closed phase A advances, but at an absurd rate (~20 s per exchange
with tracing active). The cause is the other half:

`cpu_enqueue_locked(target_cpu, idx)` leaves the task ready on another hart's
queue **and does not notify that hart**. An idle CPU is in `wfi()` inside the
idle loop, so it only learns on its next timer interrupt — and this kernel is
*tickless* (`nearest_timer_deadline`), so if no timer is pending on that hart,
the wait is very long.

The infrastructure already exists and is unused: `send_ipi` in the architecture
API (`crates/arch-riscv64/src/api_impl.rs:75`, over SBI) and the
`INT_SOFTWARE_S` arm of the trap handler (`kernel/src/main.rs:4855`), today
only for *TLB shootdown*.

**The fix is two pieces, not one.** Sending IPI is not enough: the idle loop
(`scheduler.rs:973`) returns to `wfi()` without rescheduling, so the hart
would wake and sleep again. It also needs the exit from `wfi()` — or the IPI
arm — to go through `do_schedule`. It is a scheduler change with system-wide
consequences and deserves its own batch, not the tail of this one.

## K-C15 · Inter-CPU bell — implemented, insufficient

`cpu_enqueue_locked` now sends an IPI to the target hart when not its own,
and the `INT_SOFTWARE_S` arm calls `schedule()` instead of sleeping again.
Before, enqueuing a ready task on another hart did not make it *run*: left
it eligible for when that hart woke for any other reason, and with tickless
scheduling that can take forever.

Measured in phase A, `SYS_IPC_FAST_CALL` returns in the same window:

| state | returns |
|---|---:|
| before K-C14 | 0 |
| after K-C14 (CPU spread) | 7 |
| after K-C15 (IPI bell) | 11 |

Also all 12 of 12 replies now reach their destination, so **delivery is
closed**. What remains is performance: ~13 s per exchange, still not letting
any child reach its 32-iteration milestone.

### Una hipotesis mia que resulto falsa

Seeing it still slow, I guessed the culprit was the `sfence.vma` in the
IPI handler: under TCG a global flush discards the emulated TLB, and
I had just put it in the path of **every** inter-CPU wakeup. I removed it and
remeasured: **11 -> 10 returns**, no difference. The hypothesis was false
and I note it so no one inherits it as a finding.

The removal stays anyway, for a different and verified reason: **no TLB
shootdown sender exists in the tree**. `send_ipi` had no callers until this
change, so that `sfence_vma()` was guarding a message that never arrived.
Whoever adds real shootdown **must not restore it here**: needs a per-hart
reason bit and flush only when that bit is set, or every wakeup pays it again.

### What remains open

The remaining bottleneck is unidentified. Ruled out by measurement: wakeup
delivery, CPU spread, TLB flush, and the trace itself (six UART lines per
exchange are ~1 ms, not 13 s). Next step is to instrument the test program,
not the kernel: not verified that all eight children are actually advancing,
and eleven returns split eight ways is consistent with only one or two progressing.

CI after these changes: **56 pass, 1 fails** — identical to before touching
the scheduler, including PiMutex and real-time scenarios, which are most
sensitive to this.

## Phase A: REAL cause identified, and two theories of mine disproven

Scaling down to **one client and six iterations**, phase A **passes
entirely**:

```
ok  A/server served every call     rc=6
ok  A/child completed every call   rc=6
ok  A/reply != own request (IPC-2) rc=0
ok  A/child never refused          rc=0
all=6 of 6 OK
```

So fast-IPC round-trip **works from ring 3**, and **IPC-2 is verified from
ring 3** in addition to the host suite. That is new: this path has never
been executed in kernel history.

With **two** clients and ten iterations, child 0 completes its ten and child 1
**does not even announce itself**. The server waits for N, so phase never ends.

**Phase A's cause is not performance: it is K-C12**, the `fork()` child
that returns a positive TID and never executes an instruction. One lost child
hangs the entire phase, regardless of scale.

### Two theories of mine that measurement disproved

1. **"It's the `sfence.vma` from IPI."** False: removing it gave 11 -> 10 returns.
2. **"It's contention / throughput with 8 clients."** Also false: with one
   client exchanges are immediate. The ~13 s per exchange I inferred was an
   artifact of dividing total returns by the time of a run that was hanging
   waiting for a child that never launched.

I note them because chasing a wrong theory cost more here than fixing any of
the real defects.

### New clue on K-C12, not closed

In the two-client run **two** `[PAGE FAULT] Instruction page fault at 0x0`
appear and **zero** `Killing user task`. A task jumps to address 0 and the
kernel **does not kill it**: demand paging maps page zero and lets it keep
executing zeros. Whether or not it is the cause of K-C12, that
`handle_demand_fault` accepts VA 0 is a defect by itself — the zero page
must never be demand-mapable.

The symptom is sporadic and does not correlate with any specific change
(appears in the 2-client run but not in 1, 4, or 8), pointing to a race in
`fork`, not a regression.

### On test scale

Original lane E constants are restored (8 children × 200 iterations).
**Reducing them until the scenario passes would be tuning the test to go green
on broken kernel** — exactly the mistake this audit has been documenting all
session. The scenario stays red, now for an identified cause: K-C12.

## `lease_tick` truly measured — and my suspicion was false

I suspected expanding `lease_tick` to also expire `Pending` leases had made
it more expensive, because it runs in the timer ISR. **It has not.** Measured
on the **compiled RV64 artifact** (`llvm-objdump` on the real symbol), not
QEMU wallclock:

- **Widening the predicate costs ZERO instructions** on the non-expiring path.
  `Pending` and `Active` are adjacent discriminants, so the compiler emits
  `(state-1) < 2` — a single `bgeu`, exactly what it would emit for `== Active`.
  Counting "abstract comparisons" would report a delta that does not exist.
- **The ceiling did not move**: 349 instructions before and after. What changed
  is *which table states* reach the ceiling, not the ceiling.
- The only unconditional real cost was **another** change from this audit:
  `lock()` -> `lock_irqsave()`, **+8 fixed instructions on every tick**.
  Necessary (same-hart deadlock), but not what I suspected.

Absolute cost against the tree's own criterion
(`WCET_BOUND_TIMER_ISR_US = 10`, whole ISR budget): worst case **0.93
µs with warm cache (9.3%)** and **5.2 µs cold (52%)**, at 1 IPC and
the VF2's DVFS floor (375 MHz), where WCET must hold. Fits even cold.

**Method, which is the lesson**: the instrument I used — the 1 ms `[ISR-WCET]`
diagnostic threshold under QEMU — was too coarse and also sensitive to host
load; it produced a spectacular false positive. Counting instructions in the
RV64 binary is deterministic, does not depend on the machine, and gives the
number that really matters for an ISR.

### Unapplied recommendation

Worst case is not the problem: the problem is **common case pays 157
instructions to do nothing**, and 39% of that is fixed cost. On this
robot the normal state is "no leases with deadline".

1. Atomic counter of leases with deadline and early exit.
2. **Necessary condition**: change signature to
   `lease_tick(now, out: &mut [...]) -> usize`. Bare early exit
   **saves nothing**, because the function still materializes 256 B of
   return buffer — 32 unconditional stores, fully unrolled.

Forces touching `lease.rs` and the drain loop in `kernel/src/main.rs` at once.
Described, not done.

## Fast-IPC finally delivers the request — CLOSED

The `SYS_IPC_FAST_ACCEPT` arm returned the slot index and **discarded the
caller's TID and four words**, while its own comment promised
"data words in a1..a4 (written via TrapFrame by waker)". Nothing in the tree
wrote those registers. Fast-IPC was not an RPC transport: the server could
reply, but never based on what was asked.

Now delivered **in registers** (`a1` = caller TID, `a2..a5` = words), not via
user pointer. The alternative cost a per-page permission walk plus 40 B copy
**on every accept, forever**, on the sole path whose reason for existing is
moving <=32 bytes without touching user memory — the tree already measures
that kind of cost: `sensor_read` pays +352 ns over the 1879 ns floor for a
cap-hit plus 24 B copy.

Two implementation details that are not obvious:

- **`reg_snapshot` is a copy**, and it must be (`frame.regs[10]` is overwritten
  with the return, and a forked child must inherit the file as it was at
  `ecall`). A `&mut` on it does not reach the frame: hence the output structure.
- **`SyscallOut::written` is not decoration.** `a1..a5` are *argument*
  registers and all `libsys` wrappers pass them as `in("aN")`, operands rustc
  can assume untouched. Writing them unconditionally would be UB on ring 3
  across the tree.

Verified from ring 3, phase E of `userspace/ipctest`:

```
E: server slot=0 from=121 delivered=1 w0=14680185
ok  E/server accepted the call
ok  E/server received the request payload
ok  E/server saw the caller TID
ok  E/server saw the exact request words
ok  E/client got the transformed reply
```

The `from=121` is the client's real TID. Before wiring that field was
`4294967295`, a sentinel preloaded in `a1` deliberately: returning untouched
proved **no one wrote the register** — not even a silent zero confusable with
data. Incidentally proved `trap_entry.S` does restore `a1..a5` from the frame,
so the return half already worked.

`SYS_IPC_FAST_CALL` still returns **one** word of reply. The mechanism would
work the same for the other three, but requires a dedicated wrapper (current
uses `in("a1")`, would be UB). Remains as separate work.

## Zero page no longer mappable — CLOSED

`handle_demand_fault` accepted VA 0: a task jumping to NULL got the zero page
demand-mapped and **kept executing zeros** instead of dying.
Now every VA below `USER_GUARD_LIMIT = 0x1_0000` is unresolvable.

The threshold is not invented: the nine `user.ld` files in the tree start at
`0x10000`, and parsing headers on all ten binaries in `build/` **all give**
`min PT_LOAD p_vaddr = 0x10000`. It is the widest guard possible without
touching any real image.

`handle_cow_fault` had the same hole, narrower but reachable: breaking COW
requires a page already present at that VA, and the ELF loader bounds `p_vaddr`
**only from above** — nothing rejects `p_vaddr == 0`. Closed too.

Demonstrated with hand-made ELF (`jalr x0,0(x0)` at `0x10000`):

```
[PAGE FAULT] CPU 3 — Instruction page fault at 0x0
  sepc: 0x0  task: autorun
  null guard: VA < 0x10000 is never mapped (null pointer dereference)
  resolved so far: 0 COW, 0 demand
[PAGE FAULT] Killing user task
```

**Pending in another lane's file**: `load_elf_into` still has no lower bound
for `p_vaddr`. `USER_GUARD_LIMIT` is the constant it needs.

## Fault log no longer lies

The arm printed **before** attempting to resolve, so every COW fault from
`fork()` — which resolves fine — read as fatal. Real cost measured this
session: half an hour of wrong diagnosis per run, mine and an agent's.

Now prints only what truly could not resolve, and the fatal path keeps
**all** the information it had (CPU, cause, `stval`, `sepc`, task name,
register dump, and S-mode `trace_dump`) plus two new lines:
null guard when it applies, and a counter `resolved so far: N COW, M demand`
making visible in post-mortem what no longer prints. Cost on common path:
one relaxed `fetch_add`, zero UART.

Measured with the **same disk binary** in both runs: 3 blocks before,
**0 after**.

## K-C16 · `tp` controlled by ring 3 — CLOSED

`tp` carries the hart id in this kernel: `current_cpu_id()` is literally
`mv {}, tp`, and all `PER_CPU[...]` depends on it. But `trap_entry.S` saved
the user's `tp` and **never restored a kernel one**, so after any trap from
ring 3 the kernel ran with whatever value the user had set. An unprivileged
task writing `tp` before an `ecall` made the kernel think it was on another hart:
ready queues, current task, scheduler state, all indexed to the wrong slot.

Fix: **per-hart trap vectors, indexed by `stvec`**. `stvec` is a per-hart CSR,
written once at startup, ring 3 cannot touch it, and it is correct at the
**first** trap — no bootstrap hole. Each vector carries its hart id in the
word immediately before the entry point.

Cost: **+3 instructions entering from U** (`csrr stvec`, `lw`, `bgez`),
+2 on exit, **0** on S-mode traps and context switch. Total syscall round-trip: +4.

Rejected the alternative of tagging `sscratch`: it already carries kernel SP,
and tagging it forces touching all its writers — including two in Rust — and
leaves a hole exactly where it matters (the first trap after `sret_to_user`
sees an untagged value).

### A detail that almost broke it silently
The assembler **compressed** each vector's `j` to `c.j` (2 bytes). With the id
word placed *after* the jump it would land at +2 and each hart would read the
next vector's opcode as its own id. Placing it before makes `.balign 8` fix
its offset at -4 without depending on `.option norvc`.

### K-C16b · A second bug, same file
`trap_return` reloaded `tp` from frame **also when returning to S mode**.
Sequence: task trapped by timer on hart 2 (frame `tp`=2), migrated, `context_switch`
restores `tp`=3 per K-A11, and `trap_return` overwrites it back to 2 before
`sret` to kernel code running on hart 3. Exactly K-A11 corruption by another
door. Now `tp` restores only when SPP=0.

### Collateral finding: boot hart is not always 0
Measured on QEMU virt: in one run the boot hart was **2**. The fix does not
depend on it, but `smp.rs::wake_harts` documents the opposite assumption
("contiguous ids and boot hart = 0") and `find_least_loaded_cpu` starts with
`min_cpu = 0`. Preexisting, not closed.

### Evidence
Read from the **QEMU monitor**, not kernel log: each hart has its own `stvec`
slot and that slot's word is its id. Real U-mode traps with `-d int`: six
U-mode `ecall`s, all via the table path, on a hart other than boot, with
`SYSCALL_TEST ALL PASSED`. Clean builds in `default`, `qemu`, `no-mmu`,
`rvv`, and `no-ml`.

`MAX_HARTS` was duplicated by hand in two `.S` files; now injected with
`max_harts = const MAX_HARTS` in both `global_asm!`, same technique already
used by `context_switch.S`. Verified launching with 4 harts and 0 panics.

## Null base in `brk` allocators — CLOSED

`sys_mmap` and `sys_alloc_demand` take `update_user_brk(0)` as base, and a
task whose `brk` was never initialized reports **0**: they reserved a range
from VA 0 and returned `0` as success. A null pointer indistinguishable from
a real address.

The zero page guard converts the first access to task death instead of silent
success over zeros, but **delivering a null base is still the defect**. Both
allocators now reject it, using the same constant `vmm::USER_GUARD_LIMIT` —
single source.

Verified: `ABITEST ALL PASSED`, 51 checks.

## `tp` under `rvv`
`context_switch_rvv.S` does not touch `tp` and **must not**: under that build
nothing changes it after startup, so it is hart-invariant by construction.
The K-A11 accounting in `scheduler.rs` is dead code there, and harmless.
**Before K-C16 it was not**: user-poisoned `tp` would persist forever on
that hart with nothing to fix it. Documented in the file.

## K-C12 · `fork` children never running — CLOSED, and it was not `fork`

Instrumenting the first instruction of `fork_child_entry`: the lost child
**never enters**. Does not reach `sret_to_user_forked` or execute a user
instruction. The clue about jumping to VA 0 was real but **is a separate
defect**, did not recur in ~10 runs.

The cause was **CPU placement**. `find_least_loaded_cpu()` counted **queued**
tasks — a metric blind in two ways: it does not see the *running* task
(not on any queue) and ignores priority, while `cpu_dequeue` is strict priority
without aging. A child with priority 16 placed on a hart saturated by fixed-rt
tasks stays `Ready` forever. Correlation measured over 104 forks:

| hart | children placed | executed |
|---|---:|---:|
| 2 (no RT residents) | 98 | **98** |
| 0 (`rt-motor` + `flight-ctrl`, p8) | 3 | **0** |
| 1 (`imu`, p8) | 2 | **0** |

Replaced by `find_best_cpu(prio, exclude)`, which scores **residency** and
orders by `(rt_blocking, blocking, total)`. Two failed attempts before getting
it right, both documented in code: sampling the running task is not enough
(RT tasks are periodic and there are windows where hart 0 samples empty),
and ordering by `(blocking, total)` is not enough either (harts tie and
`total` breaks ties, favoring hart 0 precisely because prior children went
elsewhere). After: **105 forks, 105 children executed, 0 lost**.

Documented residual: still placement, not anti-starvation guarantee. If all
harts were saturated by higher priority, a low task would still starve — that
requires aging and affects RT/PiMutex guarantees.

### And the queue duplicates were real
`cpu_enqueue` protected overflow with `debug_assert!`, compiled out in release.
Now `Task::queued` claims with a `swap(true, AcqRel)` — not test-then-set,
because `CPU_LOCKS[cpu]` only serializes enqueues *on one* hart and two harts
enqueuing the same task on different CPUs do not exclude.

Duplicates were not hypothetical: measured on `imu`/`odom`/`sensor-slow`.
Origin: `wake_expired_timers` runs in the timer ISR on **every** hart and
reaches `try_wake_task`, whose `state != Blocked` test and `state = Ready`
write have nothing between them. Each duplicate pushed `count` toward ring
size.

## K-C17 · Broken publication of `state` and `wait_reason` — CLOSED (partial)

`block_current` wrote **`state = Blocked` before `wait_reason`**. Every directed
waker reads `state` and only checks `wait_reason` if it sees `Blocked` —
and if the reason does not match it takes the `Mismatch` branch, which
**deliberately leaves no `wake_pending` flag**.

With that order, a waker on another hart could see `Blocked` while
`wait_reason` still held the *old* value (`None`, from when the task ran).
The predicate failed, the waker classified it as genuine mismatch,
released the wakeup without flagging, and the task slept forever on an
already-satisfied condition.

Symptom: a fast-IPC server blocked on `FastIpcServer(tid)` with a client on
`FastIpcClient(slot)` and the slot `Pending` — both sleeping, work present,
nothing `Ready`. Intermittent, contention-dependent, and indistinguishable
by inspection from a missing wakeup call.

Fix: reason first, `Release` barrier, state after; and `Acquire` barrier
on the three readers after seeing `Blocked`.

**Improvement measured, not elimination.** Before: phase A stalled with 6 of 8
children. After: **2 of 3 complete runs** (1600/1600, `ALL PASSED`), and the
failing one reaches **7 of 8**. A residue of the same family remains unidentified.
The CI scenario stays **red**, now from intermittence not certain hang.

### K-C17 residue: evidence from the stuck run

## K-C17 residue: identified — reply there, client asleep

### The instrument
`ipc-trace` did not work: six UART writes per exchange move timing enough
to **hide** the race — measured, the build with tracing reaches `ALL PASSED`
8/8 where the build without tracing stalls. Heisenbug.

New instrument, feature **`ipc-census`**, deliberately **independent of
`ipc-trace`**: a kernel task that every 2 s (blocked on `WaitReason::Timer`,
not in a yields loop that would compete with the race itself) prints
`fast_ipc_census()` — three integers under a single lock — and **only when
they change**, so a stall appears as the last line before silence.

### The verdict
```
run 1 (passes, 8/8):     pending=0 accepted=0 replied=0
run 2 (stalled, 7/8):    pending=0 accepted=0 replied=1
```

**One slot in `Replied`.** The server replied, the reply is deposited,
and the client **never picked it up**.

This rules out both hypotheses on the table:
- **Not `Pending`**: the server did not lose a wakeup.
- **Not `Accepted`**: the server did not forget to reply.

And **corrects** my earlier attribution — "server stalls" — which I had
inferred from the variance in children completed (5, 6, 7 of 8). The variance
lied: **one client** dies, the chain stops behind it.

Frequency measured with machine quiet and fresh disk image each run: **2 of 6**.
The "2 of 3" I reported before was luck.

### Where to look now
The fault is between `fast_ipc_reply` returning the `caller_tid` and the
client picking it up. Candidates, in order:

1. **`wake_task_by_tid` classifying as `Mismatch` a valid wakeup.** That
   branch **leaves no `wake_pending` flag** deliberately. If the client is
   `Blocked` on `FastIpcClient(M)` and the wakeup for slot N arrives, it is
   discarded — correct for stale wakeup, fatal if slots get confused.
2. **The 8-turn limit on `FAST_CALL` retry loop.** If the client exhausts
   eight before the reply lands, it returns -1 and the slot stays `Replied`
   forever — exactly the observed state. This fits the evidence **without
   needing any lost wakeup**, and is cheapest to check: just count the
   stalled child's `refused`, which today do not print because it never
   terminates.
3. The documented slot ABA.

Candidate (2) is what I would investigate first: requires no exotic race,
just eight clients against one server generating more than eight spurious
wakeups in a window.

## The residue is NOT one bug, it is at least TWO — and one is security

Layered instrumentation (`ipc-census`, independent of `ipc-trace` because
tracing hides the race) separates the residue into two distinct failures.

### Scheduler exonerated with numbers
Counters on `wake_task_by_tid` in stalled runs:

```
wake: dispatched=2608 stamped=114 MISMATCH=0 absent=0 enq_refused=0
```

**Zero wakeups discarded.** The `Mismatch` branch — the only one that releases
a wakeup without flagging — never fires. Also ruled out by measurement:
starvation (queues stay balanced, `rq=[2,2,3,1]`), stale `queued` claim

### Fault A — client asleep, reply already deposited
```
pending=0 accepted=0 replied=2 | blocked_on: fastclient=2 ...
```
Two clients blocked on `FastIpcClient`, two replies uncollected. With
`MISMATCH=0`, the wakeup **was not lost in the scheduler**: either it never
emitted, or the client consumed it and still did not pick up. Not closed.

### Fault B — K-C18: ring-3 task jumps to kernel code
```
[PAGE FAULT] CPU 2 — Instruction page fault at 0x80244110
[PAGE FAULT] Killing user task
```
That run `replied=0` and `fastclient=0`: **the missing child was not blocked
in fast-IPC at all**. It was dead.

`0x80244110` falls inside kernel `.text` (`_start` = 0x80200000,
`_text_end` = 0x8027532a), in the `robot_os_sched::wait` zone. An unprivileged
task tried to **execute kernel code**. The guard did its job and killed it —
no escalation — but a ring-3 jump register containing a kernel code pointer
is a live leak.

It is the symptom of K-C11 (`sret_to_user_forked` now restores the parent's
entire register file, and `ra` should be a user address), so **the K-C11 fix
is incomplete or there is a second path**. Does not happen on clean boot
without forks: 0 page faults. It is on the `fork` path.

**Priority**: A is an availability nuisance; **B is security** and goes first.
It also explains why stall frequency seemed erratic: two distinct causes
adding up in the same measurement.

### Tool that stays in the tree
Feature `ipc-census`: kernel task that every 2 s, and **only when something

reason, queues by CPU, the two impossible states (`ready_unqueued`,
`blocked_queued`), and wakeup decision counters. Blocked on `WaitReason::Timer`,
not in a yields loop that would compete with the race. Independent of `ipc-trace`
deliberately.

## K-C18 · Ring-3 task jumping to kernel code — CLOSED

`sret_to_user`, the fresh exec path, zeroed **only `a0`–`a7`**. A newly loaded
process entered its entry point with `ra`, `gp`, `t0..t6`, and `s0..s11`
holding whatever the kernel task that ran the loader left. Observed:
`regs[1] (ra) = 0x8020198a`, a kernel text address, delivered to ring 3
**on every exec**.

Two consequences:

- **Leak.** Defeats any layout randomization and hands an unprivileged task
  a free layout oracle.
- **Crash.** Nothing in the ELF entry ABI defines those registers, so a
  program can `ret` from a leaf that never set `ra` — and that jumps straight
  to kernel text. Measured: `[PAGE FAULT] Instruction page fault at
  0x80244110`, inside `_start`..`_text_end`, task dead. The guard held,
  never escalated, but that pointer had no business being there.

**And K-C11 made it inheritable.** Now that `fork` faithfully copies the
parent's register file to the child, a parent that never overwrote its garbage
`ra` passed it on. The loader is where it needs cutting; the `fork` path does
right to copy what it finds.

Fix: zero **all** general-purpose registers. `sp` gets loaded with user stack
and `tp` is deliberately left with the kernel's hart id — touching it is
the only way to reintroduce K-A11. Checked before doing it that no `user.ld`
defines `__global_pointer$` and the binary does not use `gp` once, so zeroing
breaks nothing.

Verified: three runs, **0 page faults, 0 dead tasks**. Before appeared in
roughly one of every two.

## K-C24 · `Blocked` does not mean parked — the REAL family residue, caught in QEMU (23-08)

**The first QEMU run after the entire batch cold-failed phase A** (8 `Pending`
slots, 0 exchanges) — worse than the 22-08 residue. Census expanded with
identities (`ready_unqueued_ids`, new tool) named the victim: `autorun` (phase A
server), **`Ready` without being on any queue, forever**, with `enq_refused=0`
and `MISMATCH=0` — all counters clean.

**The mechanism** (verified against code, and also explains the "Replied +
sleeping client" signature from 22-08 — this was the K-C17/K-C19 family
residue we never closed, with clients as victim then):

1. `block_current` commits `Blocked` and calls `do_schedule`; if the queue is
   empty, `do_schedule` **returns without switching** and the task keeps
   executing its caller's retry loop with `state == Blocked` and
   `context_saving == true`.
2. A waker sees `Blocked` → dispatches it (CAS→`Ready`) and **enqueues a
   running task**.
3. Its own hart dequeues it as `next == old` → return early: the queue entry
   is consumed without switch.
4. At the next tick, `do_schedule`'s re-enqueue arm only saves currents in
   `Running` — a current in `Ready` is not re-enqueued and vanishes from all
   queues. Permanent starvation with no dirty counters.

**The closure — "no task is dispatchable until its context is saved"**, in
three pieces over the `state_word` protocol:

- `wake_transition` gains `saved` parameter (the three wakers derive it from
  `!context_saving`, whose publication travels free with the Release commit):
  `Blocked` + matched reason + **not saved** ⇒ **flag, never dispatch** —
  also works for broadcast sweeps, because matching the reason under `Blocked`
  identifies the target. Under `rvv` `true` is passed (that build never keeps
  the flag; its documented gap does not change).
- `commit_blocked_or_consume_wake` consumes the flag **and normalizes to
  `Running` in the same CAS**: re-entry of a no-switch block that consumed
  and kept running with `Blocked` in the word would re-expose the bug when
  clearing `context_saving`.
- `do_schedule` gains `Blocked`+flag arm on switch-out: a flag is a wakeup
  **already delivered**; parking the sleeping task with it loses it
  (no one will warn again). Converts flag→`Ready`+enqueue at the exact point
  the task leaves CPU, with `context_saving` still high — the dequeue
  spin-gate recovers its original purpose and becomes bounded again.

With this, `Blocked`+flag goes from "unrepresentable" to **representable only
by the not-saved arm**, and the two exits (consumption on next commit, or
sweep by dispatch CAS when waking an already-parked task) deliver the wakeup.
`sched-wake-tests`: 67 → **71**, with the four K-C24 regressions executing
the real protocol.

**Tool that stays**: `ready_unqueued_ids` — the twin with identities of the
`ready_unqueued` census counter; who is in the impossible state,
not just how many.

   at the end of **every** U-mode ecall on every hart: another hart completing
   any syscall in the window consumes the context and SRET to another task's
   newly-built space, while the victim — whose SATP already switched — resumes
   its old sepc under the new table. Two simultaneous SYS_EXEC also trample
   the slot and leak the first's page table. Exactly the pattern K-A15
   eliminated for `fork`; exec lagged behind. Fix: context in per-task slot
   with identity check (mirror of `fork_ctx_ready`).
2. **K-C22 (MEDIUM) — exec-on-exec leaks old address space.** `exec_user`
   overwrites `user_pt` without destroying the old table; SYS_EXEC loop drains
   the PMM on success path. Sibling to `task_exit` leak already filed in
   KERNEL_REVIEW_NOTES — close both together (the class, not the instance).
   Note: destroy only after SRET to new space.
3. **K-C23 (MEDIUM) — fragile contract of `mark_context_saved`.** Called on
   old task's stack and publishes "stack free" with its Release; today compiles
   to leaf without frame and nothing reads after the store, but any future
   prologue (kprintln, wcet probe, dev build) converts its epilogue to an
   S-mode race against the hart that already restored that stack.
   Fix: set flag from asm itself (`fence rw,w` + store with offset injected
   by `const`, like `task_satp_off`).
4. **(MEDIUM, cross-repo) — kernel reboot jams kernel→brain direction.**
   `SEND_NONCE` seeded from `clint::get_time()` (restarts ~0 on reset) and
   brain `Receiver` is process singleton with persistent `rx_high_water`:
   after reboot all kernel traffic lands as replay until server restarts.
   Design decision pending (yours): recreate Receiver per-connection when AEAD,
   and in HMAC-only persist nonce or derive from RTC.
5. **(LOW, brain) — sleeping rekey stubs** (`LABEL_REKEY`, `_rekey_counter`)
   with no kernel counterpart: delete them or specify rekey in a two-repo RFC
   before anyone connects them.
6. **(INFO)** `resolve_only_untrusted` depends on `lto = false` (already
   noted by the setting in Cargo.toml); `set_task_fork_ctx` "unreachable"
   failure path does not destroy `child_pt`; `link-encrypt-enforced` QEMU
   scenarios pending writing when QEMU returns (pair reject/launch, cloning
   link-auth ones).

## K-C19 · The final flag window — CLOSED (2026-08-23)

**Design**: state and flag now live in a single **`AtomicU32`** per task
(`Task::state_word`: bits 0–2 state, bit 3 flag), with two symmetric
conditional CAS (`crates/sched/src/task.rs::sched_word`):

- **Committing `Blocked`** requires flag = 0. If the CAS fails, retry
  consumes the flag and **aborts the block** — structurally impossible to
  sleep over a pending wakeup.
- **Flagging** requires state ≠ `Blocked`. If the CAS fails because commitment
  landed first, retry sees `Blocked` and **dispatches** — structurally
  impossible to leave a flag no one will consume.

Each CAS only fails because the other side succeeded, so loops are bounded in
practice to one extra iteration. No locks: no lock-order problems with ISR, and
no reversed-handshake race (waker never dispatches a task that did not commit
`Blocked`; blocker never enters `do_schedule` with pending flag). The `wait.rs`
invariant — "Blocked with flag does not occur" — changes from call-site
discipline to structural impossibility. The K-C17 fences subsume into the
Acquire/Release orders of the CAS.

**Verified**:

- Protocol is free functions on `&AtomicU32` — `sched-wake-tests` executes
  **the kernel's real code**, not a replica (retired the hand model from K-C9
  section, which was exactly the test-replica trap).
  67 tests including: flag cannot commit, committed cannot be flagged,
  `Blocked`+flag unreachable in 27 serialized interleavings, and
  **stress of 20,000 rounds with two real threads** that fails if a single
  wakeup is lost or dispatched without commitment.
- `ci_check.sh` with `CI_SKIP_QEMU=1`: **40/40** (13 builds, 23 host suites).
- **Counted on RV64 artifact** (`llvm-objdump`, tree criterion):
  `try_wake_task` 191 instr / 1 lr-sc pair, `wq_wake_by_tid` 190 / 2,
  `wake_task_by_tid` 222 / 2, `wq_block_current` (with `block_current`
  inlined) 70 / 2. **Zero panic references in all three wakers**
  (run in ISR). Only panic reference in `wq_block_current` is the preexisting
  bounds-check on `TASKS[idx]` (bound 64), present before the change; noted
  below as minor pending.

**Pending when QEMU returns**: repeat stall frequency measurement (was ~1 in
3 runs with identical signature) on phase A of `ipctest` — host closure proves
the protocol, not the whole system.

**Minor pending (preexisting, not this batch)**: `task_mut(idx)` in the block
path emits `panic_bounds_check` against `MAX_TASKS` because `current_idx` only
compares to `usize::MAX`. The same provable-guard trick from `lease_tick`
(`if idx < MAX_TASKS`) would eliminate it.

## K-C19 · The final flag window — original diagnosis (historical)

With K-C18 out, the remaining stall is isolated and **identity instrumentation
proves it**:

```
slot idx=2 state=Replied caller=124 server=18
blocked tid=124 client=true payload=2
```

Match exactly: reply is deposited, addressed to that client, and client sleeps
on that slot. Three runs, identical pattern. Every wakeup counter clean:
`dispatched=2613 stamped=279 MISMATCH=0 absent=0 enq_refused=0`, `used`
synchronized, queues balanced.

**The window.** `block_current` consumes the `wake_pending` flag and *then*
marks itself `Blocked`. A waker reading `Running` between those two operations
takes the `StampPending` path and leaves a flag the task has already passed.
No one consumes it. Permanent sleep, with wakeup emitted and accounted.

### The fix I tried and reverted
Double-check handshake: recheck the flag after marking `Blocked`, and in
`wake_task_by_tid` re-read state after flagging. **Works — `late_dispatch=2`
in one run, two hangs prevented — and I reverted it anyway**, because it
introduces a worse race: if the waker wins the flag `swap` and enqueues the
task while it, having lost that `swap`, proceeds to `do_schedule`, the task
ends up both "current" and on a ready queue. Observed: **system freezes at
boot**, 391 lines and 24 total wakeups vs ~2500, even GPIO check failing.

Freezing the board is worse than losing a wakeup. A robot kernel with
`panic = "abort"` is not fixed by a patch that sometimes freezes boot.

### What is needed
State and flag read and written under the same exclusion: one lock per task,
or a single atomic encoding both (`state` and `wake_pending` in one
word with CAS). It is a structural scheduler change, touches all wakers, and
deserves its own batch with a clear head.

Current stall frequency with K-C18 closed and without the handshake:
**approximately 1 of every 3 runs**, always with the same signature.

## Fast-IPC ABA — CLOSED (generation tag, approved by user)

63-bit handle in `a0`: **57 bits generation, 6 index**, bit 63 always zero by
construction (`((2^57-1) << 6) | 63 == 2^63-1`), with a compile assertion
that breaks the build if someone raises `MAX_SLOTS` to 128 and indices start
aliasing within the generation field.

**2^57 reuses of a single slot before wraparound.** At one per nanosecond —
faster than a retire on this core — that is ~4.57 years doing nothing else.

Generation increments **only on free**, with `wrapping_add` (with
`overflow-checks = true` a `+1` at the ceiling would panic and reset the board;
it is the right arithmetic: it is a tag, not a counter). Cost on hot path:
one comparison, two masks, and an `or`, inside the lock already being held.

### Two design decisions worth not undoing

**Check order is state → ownership → generation**, and that makes `Stale`
and `Refused` **not a partition**: a stale handle whose slot was freed comes
back `Refused`, indistinguishable from "does not exist". Deliberate. If
generation was checked first, `Stale` would be a **generation oracle**: any
ring-3 task sweeps 64 indices and reads how many times each slot has rotated
on the board. Same reasoning already applies to `fast_ipc_wait_state`.

**`privileged` skips ownership but NEVER generation.** Ownership is authorization;
generation is exchange identity. A kernel server with a dead handle is just as
wrong about reality as a user one, and writing would corrupt the current tenant.

### New ABI rule
`fast_ipc_handle_slot` **rejects** `handle > i64::MAX` instead of masking bit 63 —
first test run caught it: `1u64 << 63` alone decodes to slot 0, generation 0, so
a server that cached a negative return and sent it would land on a live slot.
**libsys must pass `a0` untouched: no mask, no sign extension.**

### The wiring that broke silently
None of this raised a compile error: `fast_ipc_accept() -> Option<usize>`
kept returning an index, and `ipctest` computes `REPLY_MAGIC + slot` and
validates `w < REPLY_MAGIC + FAST_IPC_MAX_SLOTS` — with a 63-bit handle
that arithmetic produces garbage and phase A fails **at runtime, build
green**. Fixed by making `FastRequest` carry **both** fields: `handle`
(opaque, what REPLY takes) and `slot` (decoded only where it knows the
layout, just for logs and arithmetic).

54 tests (40 prior + 14), verified by hand. Include generation wraparound
**as a test** — sets the counter manually and proves ABA reappears — instead
of leaving it as an assertion.

### Residual
The **client** side of ABA stays open: `WaitReason::FastIpcClient(u32)`
carries the raw index and is a `crates/sched` type. `fast_ipc_wait_state`
contains it by `caller_tid` (a reassigned slot reads `Gone`), does not
eliminate it.

## K-C20 · RWX page reachable from ring 3 — CLOSED

**The session's gravest finding, and it came from an unrelated task.**

The ELF loader's flag derivation was **binary**: writable →
`USER_RW`, **everything else** → `USER_RX`. A read-only segment
(`p_flags = PF_R`, no `PF_X`) mapped **executable**.

Full exploitation, not theoretical: an image with an RW segment and behind it
an `R` segment sharing its page goes through the page-reuse branch with
`add = USER_RX`. `add_user_leaf_perms` only rejects WRITE-on-EXEC
—the asymmetry I myself introduced closing the page-layout bug—, so
**EXEC-on-WRITE passes** and the page ends up **R+W+X**. The `entry_ok`
satisfied by a third `PF_X` segment well-formed. Ring 3 writes instructions
there and jumps to them. W^X broken by an image the loader accepts as valid.

Closed with three-way derivation (`PF_W` → RW, `PF_X` → RX, rest → **RO**)
and explicit reinforcement in reuse branch: `EXEC` on an already-mapped page
→ rejection.

**Honest scope**: lives in `load_elf_into`'s map loop, which has **zero host
coverage** and could not run without QEMU. Closed by inspection. Changes PTEs
of `.rodata`-exclusive pages across all binaries (RX → RO); verified page-by-page
on the 12 ELF that shared `.text`/`.rodata` page stays RX. **Pending QEMU
verification: `abitest`**, the binary that has historically caught permission
regressions here.

## ELF loader lower bound — CLOSED

`p_vaddr < vmm::USER_GUARD_LIMIT` → rejection, with the constant coming from
`vmm` instead of declared again. The comparison is `<`, not `<=`: a `<=`
kills all userspace, and without QEMU **only the test detects it** — verified
by mutation, kills 8 tests.

Also bounded **segment order** (`p_vaddr >= prev_seg_end`), which the
page-reuse branch *documented* and no one checked: an ELF with
disordered `PT_LOAD` causes a later segment to overwrite an earlier one's
already-mapped page.

`e_entry` needs no bound of its own and is stated in code: only validated
within an already-bounded segment, so confined transitively. And since all
segments start at >= 0x10000, initial `brk` is now >= 0x11000,
reinforcing the null-base rejection in `sys_mmap`/`sys_alloc_demand`.

## Boot hart != 0 — HALF CLOSED, scope measured

`wake_harts` **already identified** the boot hart correctly (`current_cpu_id()`,
not a literal 0). The bug was in the seed `let mut online = 1`, which counts
the boot hart **as if it occupied slot 0**. `NUM_ONLINE_CPUS` is consumed as
**prefix bound**, so that seed only works if the boot hart is 0.

Exact scope, exhaustively tested: **breaks only if additionally some
`hart_start` fails**. Without failures, boot≠0 is harmless — why it never
appeared. With failure: boot=2 and hart 0 dead published `online=1`, meaning
"hart 0 is alive", exactly the only one that is not; every unfixed task went
to a dead hart.

Fixed with liveness bitmask and prefix derived after. `online_prefix` returns
**honest 0** if hart 0 is dead instead of forcing it to 1, which would assert
it lives.

**`boot_hart_id` was not needed here**, and is stated in the file: `wake_harts`
runs on the boot hart with `tp` already set by `boot.S`. That symbol exists
for the *trap* path, which cannot trust `tp` after a trap from U.
The defect was accounting, not identification.

### Unconditional breakage stays open
`PER_CPU` is `[_; MAX_CPUS]` with `MAX_CPUS = 4`, all access is
`PER_CPU[current_cpu_id()]` **without clamp**, and `boot.S` only range-checks
**secondary** harts (and against `MAX_HARTS = 8`, not `MAX_CPUS`). On a board
that enumerates more harts than `MAX_CPUS` — the VF2/JH7110 case already
documented in `KERNEL_REVIEW_NOTES`: S7 as hart 0, U74 as 1..4 — a boot hart
of 4 indexes `PER_CPU` out of range and **resets the board**, no `hart_start`
failure needed. The clamp belongs in `boot.S`/`kernel_main`.

## K-C5 · Mandatory encryption mode — CLOSED (user decision)

Gate **per-packet**, in `wrap`/`unwrap_consuming`, policy fixed at compile
time by `link-encrypt-enforced`. Per-packet not at establishment because the
brain loop holds the session as `Option<EncryptLink>` and **both send and
drain `match` over it**: each `None` arm is a path skipping the entire AEAD
layer, and today they are reachable because `CFG_LINK_ENCRYPT=0` is
**the default**.

The mechanism is not a flag with setter: an AEAD session counter that only
rises on completing the PSK-authenticated X25519 handshake. Decrement with
`saturating_sub` because an unbalanced `fetch_sub` would wrap to `usize::MAX`
without panic and leave **the gate open forever**.

Cost: ~3-4 instructions vs >=3 SHA-256 compressions of the envelope HMAC.
**Below 0.2%.** With policy off, cost **exactly zero**: the `const` folds
and the binary is identical.

**The RAM watermark stays**, and the reason matters:
`SecureChannel::decrypt_consuming` **carries no receive counter or nonce
window**, so a frame replayed within the *same* live session decrypts and
verifies every time. What encryption mode closes is the **reboot** window.
Removing it "because AEAD handles replay now" would have reopened in-session
replay of ESTOP and actuators.

### And a hole I was not looking for
**Camera frames bypass the envelope.** `PKT_CAMERA` sends directly over TCP,
no envelope and no AEAD, gated by `link.is_none()` — meaning fires
**exactly when no session**. With policy active it would keep pushing
camera bytes in clear while `wrap` rejects everything else. And today, even
with key loaded, **camera frames travel unauthenticated**.

### Against the secure boot trap
`policy_const_matches_the_feature_that_was_actually_enabled` asserts the
`const` value in **both** states, so a renamed or mis-forwarded feature
breaks the suite instead of disarming the gate to green. The policy is
`cfg!`, not dependent on any disk file.

## Closure 2026-08-24 — K-C25: the K-C17 residue was an orphaned wake stamp

The "unidentified throughput bottleneck" this audit left open (~13 s/exchange
on 22-08, ~1 exchange/s after K-C24, hidden by `ipc-trace`) is **closed**, and
it was never throughput.

**Method.** QEMU `-accel tcg,thread=single -icount shift=3` (virtual time
coupled to executed instructions) turned the 1-in-3-battery wedge into a
1-in-2-runs reproduction, and the `ipc-census` feature (2 s cadence,
print-on-change only — cheap enough not to close the window, unlike the
trace) captured the wedge live. Under `-icount` phase A completes 1600/1600
exchanges in ~30 s — the "slowness" under MTTCG was the wedge striking
serially, one client at a time.

**Mechanism (K-C25).** `wake_transition`'s K-C24 `!saved` arm stamps a
`Blocked` task that has not finished switching out. Its doc claimed three
consumers for that stamp: the target's next commit, `do_schedule`'s
switch-away sweep, or "the next wake's dispatch CAS". A stamp that lands
*after* the sweep's check and *before* `context_switch.S` clears
`context_saving` parks the task as `Blocked + WAKE_STAMP + saved` — and for
one-shot wakes (a fast-IPC reply fires exactly once; RPC and lease returns
likewise) there is no next wake. Census evidence: client tid=126 at
`word=0xa saving=false` with its reply sitting in a `Replied` slot; the
symmetric server-side form (8 `Pending` slots, server asleep, all 8 doorbell
wakes counted as `stamped`) was captured the same day. Wake counters at every
wedge: `MISMATCH=0 absent=0 enq_refused=0` — the wakes were all *delivered*
as stamps; nothing ever consumed them.

**Fix (the class, not the instance).** `sched_word::reap_orphaned_stamp`
(one CAS: `Blocked+STAMP → Ready`, refuses anything else) +
`scheduler::reap_stamped_sleepers()` walking the pool from the timer tick
right after `wake_expired_timers`, gated on `context_saving == false`
(a still-true flag means the target's own commit or the sweep still owns the
stamp). Recoveries count as `late_dispatch` in `wake_counters` — the counter
reserved-but-never-incremented since K-C19. `Blocked+STAMP+saved` cannot
arise any other way: with `saved` true a wake dispatches, never stamps, so
reaping it is unambiguously delivering a lost wake. Host tests:
`sched-wake-tests` 71 → 75 (orphan reaped; stampless sleeper refused;
running-stamp refused — that one belongs to `commit_blocked_or_consume_wake`;
reaper-vs-late-wake race delivers exactly once, 20k threaded rounds).

**Verification.** Full battery 2026-08-24: **59 passed, 0 failed** — the
`userspace: IPC` scenario green under plain MTTCG for the first time, with
`late_dispatch` visible in census runs (the reaper earning its keep: 29-52
recoveries per run). **Qualified honestly:** that green is not yet
guaranteed — a second, distinct wedge class (K-C26 below) still strikes in
roughly 1 of a handful of MTTCG runs, so battery results stay
luck-dependent until it falls. Good runs complete phase A in ~1 s wall
clock, which is the strongest possible confirmation that the kernel was
never slow. Falsified along the way (recorded above, kept per tree
doctrine): TCP-handshake yield-storm (fixed anyway — sleep-poll), host App
Nap (caffeinate: no effect).

**Still open — K-C26** (logs preserved in the 24-08 session scratchpad:
`aba_run1.log`, `mtc_run1.log`, `mttcg_run5.log`, `fix_run6.log`,
`cur_run1.log`): a second, distinct wedge class. Terminal signature, seen
under BOTH plain MTTCG and icount: the phase-A server parked
`READY-UNQUEUED` (Ready, in no queue, current on no hart) with all slots
Pending and every client asleep — the exact state K-C24 exists to prevent,
via an unidentified genesis. Distinguish carefully: *transient*
`ready_unqueued=1` blips (a task mid-window between dispatch CAS and
enqueue) are normal and were seen pre-reaper; the *persistent terminal*
server-Ready-unqueued has only been observed after the K-C25 reaper landed,
on a pre-fix sample too small (~12 icount runs) to acquit or convict the
reaper. First-generation reaper had a real ABA (reaping a cycling task off
a recycled `Blocked+STAMP` bit pattern — census caught it enqueueing the
running server) — closed same day with the not-current-on-any-hart guard.
Next-session discriminators, in order: (1) `late_dispatch` delta across the
census window where tid=18 first goes Ready-unqueued (reaper implicated
only if it fired in that window); (2) `cpu_enqueue_locked` refusal
semantics — `do_schedule`'s K-C24 arm and Running-re-enqueue arm both
ignore its return value, a silent Ready-in-no-queue source if refusal is
possible there; (3) A/B against the pre-K-C25 binary; (4) if the reaper is
implicated, the two-tick persistence guard (reap only a `(idx, word)` pair
stable across two consecutive passes). Diagnostic tooling now in the tree:
per-sleeper `word`/`saving` in `blocked_fastipc_ids`, per-hart
`current_snapshot` in the census, and the `qemu,ipc-census` combo in the CI
build matrix so the diagnostics stay warning-clean.
