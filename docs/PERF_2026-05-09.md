# Performance audit + optimisations — 2026-05-09

> Performance audit of robot-os (47 KLoC kernel) and robot-brain
> (~30 KLoC Python). Methodology: parallel exploration of hot paths
> (kernel) and micro-issues (both). Categorised wins by impact;
> implemented contained ones, documented architectural ones with
> rationale for deferral.

## Deferred (architectural — documented for follow-up)

These are real wins (10–40×) but each is a multi-day refactor that
needs careful design and benchmarking on real hardware. Doing them
poorly would regress correctness; doing them well requires the kind
of dedicated time that an audit cannot supply.

### P1 — ML inference RVV vectorisation

**Files:** `crates/ml/src/int8.rs:55`, `crates/ml/src/ggml_nano.rs:55`.

**Win:** 20–40× on K1 (RVV 1.0, VLEN=256). 16 f32 elements/cycle vs
the current scalar loop's ~2-3 cycles/element.

**Why deferred:**
1. Requires hand-written RVV intrinsics (`vsetvl` + `vle32.v` +
   `vfmacc.vf` etc.) — Rust's stable RVV intrinsics are still
   incomplete; needs `core::arch::riscv64::vector::*` (nightly).
2. Has to be benchmarked on K1 hardware to confirm the speedup
   matches the synthetic estimate. QEMU's RVV emulation has very
   different cycle costs from real silicon.
3. Architectural decision: how many quantisation paths to RVV-ify
   (int8 dequant only? FP32 GEMM? GGUF q4_0?) is sized by hardware
   we don't have yet.

### P2 — Timer ISR `nearest_timer_deadline()` O(N) → min-heap

**File:** `crates/sched/src/scheduler.rs:1024`.

**Win:** 15× on the per-tick scan; 512 µs/sec saved at MAX_TASKS=256.

**Why deferred:**
1. Needs a `no_std`/`no_alloc` min-heap (sleeping tasks). Standard
   `BinaryHeap` requires `alloc`; the scheduler runs in contexts
   where alloc must be avoided (timer ISR).
2. Inserts/removes need to happen at every `task_block(Timer(d))` and
   `wake_expired_timers` — cross-cutting change in scheduler code
   that already has subtle SMP locking invariants we just audited.
3. Performance gain is real but absolute cost is small (~0.5
   ms/sec of CPU); not worth risking a scheduler regression today.

### P3 — Scheduler `find_earliest_deadline()` O(N) → EDF queue

**File:** `crates/sched/src/scheduler.rs:597`.

Same rationale as P2 — needs per-CPU sorted-by-deadline ready queue.
Right after P2 lands, this becomes natural.

### P4 — TCP lock-once-per-packet

**File:** `crates/net/src/tcp.rs:780+`.

**Win:** 8–10× on TCP packet latency under load.

**Why deferred:**
1. The current code acquires `TCP.lock()` at every conn-state read
   and every state transition. Refactoring to a single critical
   section requires either:
   - `RwLock` for the conn table (read-mostly access) + per-conn
     mutex; or
   - Wholesale move to lock-free state machine (`AtomicU8` for
     `TcpState` and seqlock for the conn struct).
2. Either approach is invasive and needs the full TCP regression
   test pass which we don't have on real hardware yet.
3. The recent OTA-throughput saga (5 distinct TCP bugs across 2
   sessions) suggests TCP correctness invariants are still being
   nailed down — better to optimise after we're confident.

### P7 — TCP buffer 128 KB × 8 = 1 MB → lazy/shared

**File:** `crates/net/src/tcp.rs:262`.

**Win:** ~896 KB kernel memory reclaimed in typical case (1-2 conns
active).

**Why deferred:**
1. Needs a `BufferPool` allocator that hands out aligned buffers
   from a single 256 KB pool, with `acquire/release` on
   `listen()/close()`.
2. Every conn struct then holds a `BufferRef` instead of inline
   `[u8; SIZE]` — touches every send/recv path.
3. The 1 MB "waste" is on a system that nominally has 128 MB; not a
   functional blocker. Worth doing for memory-tight platforms (esp.
   ESP32-C3 where the buffer is gated separately).

### P8 — Scheduler POOL_LOCK per-CPU

**File:** `crates/sched/src/scheduler.rs:74`.

POOL_LOCK is held during task creation only (already rare). The
real contention is per-CPU queue access, which already has
`CPU_LOCKS[]`. Diminishing returns; deferred.

### P9 — Slab allocator for hot-size kernel heap allocations

**File:** `crates/mm/src/kheap.rs`.

`linked_list_allocator` first-fit + global lock is fine at our
allocation rate (estimated 100 allocs/sec). Slab would help if we
spiked into 10 K allocs/sec, but our pattern is mostly long-lived
allocations at boot + a few small ones for IPC messages. Skipped.

### M5 — Seqlock fence relaxation

**File:** `crates/behavior/src/world_state.rs:148, 155`.

`fence(SeqCst)` could be `Acquire/Release` for seqlocks. Real win
needs benchmarking on real hardware (RISC-V Ztso vs RVTSO matters
here). Deferred.

### M8 / M9 — Brain async I/O + JSON batching

**Files:** `robot-brain/planner/experience.py:214,231`.

Currently uses synchronous `open()` from async context. Win: avoid
event-loop blocking on disk-bound experience writes. Deferred
because:
1. `aiofiles` would be a new dependency.
2. Experience writes are once per task (~minutes apart), not
   per-frame; the absolute saving is small.

JSON batching skipped because the JSONL append-only format is the
recovery story for crash safety — switching to a batched format
trades durability for throughput, which is the wrong tradeoff for
hobby/single-robot use.

## Net change summary

```
Source files modified:    9 (kernel) + 2 (brain)
Source files deferred:    7 (with rationale)
Tests:                    103 regression + 58 OTA + 1128 brain — all pass
Build:                    5/5 configs, 0 errors 0 warnings
Estimated wall-clock win: 3-5× on HMAC packet path,
                          5-10× on FAT32 small-file IO,
                          marginal but cumulative on bitmap/byte ops
```

The big multipliers (P1 RVV 20-40×, P2/P3 scheduler 10-20×,
P4 TCP 8-10×) are deferred because each is a multi-day refactor
that needs hardware-time to validate. Worth tackling individually
post-Julio when VF2/K1 cycle counters can confirm wins.

## Recommendations going forward

1. **Profile, don't speculate** — once hardware lands, instrument
   `crates/drivers/src/wcet.rs` at the deferred hot paths and
   measure. Don't optimise from estimates alone.
2. **Order:** P1 (ML RVV) gives the largest user-visible win for
   perception-heavy robots (drone obstacle avoidance); start
   there. P2/P3 (scheduler) become important only when MAX_TASKS
   approaches its cap (256).
3. **Sequence with security:** any TCP refactor (P4) must
   coexist with the recent ACK-correctness + window-update fixes;
   add tests before changing locking discipline.
